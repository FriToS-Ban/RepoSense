## What production serves now

**`RETRIEVAL_ENGINE` defaults to `v2`.** Setting `RETRIEVAL_ENGINE=v1` is the rollback; the v1 code stays for one release (design §8). The served system, **V2**:

1. **Candidates:** the union of
   - the lexical channel (BM25F with the M6 settings),
   - the structural 1-hop channel,
   - the PPR channel (α = 0.1).
2. **Learned fusion:** the M9 logistic reranker trained on T2-train **without co-change features**. Production has no commit-history index, and on T2 co-change features add nothing (F_nocc ≈ F).
3. **One rule on top:** callees referenced **on a changed line** are placed first (at most 10), in model order. This is the only post-hoc design decision in the system, and it is evaluated on all three benchmarks below. The reason: T2's labels cannot reward read-only context, so the M9 model learned to *demote* callees. T1 deps (callees by construction) and T3 (bugs whose detection needs the callee's signature) both show that a reviewer needs them.
4. **No overlay graph.** On T2 it changes nothing (M4: −.004; here +.007, n.s.), and the full graph rebuild was the largest latency cost.
5. Relation-aware packing (M2/M3) into the 12k-character budget. The production model ships in `backend/retrieval/models/`; a test asserts that it is byte-identical to the evaluated one.

Behaviour at the switch:
- **Missing snapshot.** A repository indexed under v1 has no v2 snapshot. Its first review requests a full v2 index (tarball) and falls back to v1 for that one review.
- **Pushes.** Pushes to the default branch update the graph incrementally (M7).
- **Errors.** Any v2 error falls back to v1 for that review.
- **Non-Python diffs.** A diff that touches no Python file is served by v1 (see "Not done").

## Cutover criteria (design §8)

| Criterion | Result | Met? |
|---|---|---|
| The best configuration beats S2 (v1) and A on T2 Recall@budget with p < 0.01 | V2 − S2: **+.637** [+.591, +.683], p 1e-4. V2 − A: **+.064** [+.028, +.101], p .0008 (p_holm .0024) | ✅ |
| No T1 regression | vs v1 (what it replaces): deps .049 → **.962**, impact .201 → **.995**. vs the best v2 system on T1 (E+A, circular): deps −.038, impact ±0 | ✅ against what it replaces; small loss against E+A on a benchmark that rewards E+A by construction |
| p95 latency within budget | V2 on T2, measured alone on a laptop CPU: **p50 57 ms, p95 193 ms** (mean 72). A_tuned: p50 24, p95 113. The §5.7 stage targets sum to ~170 ms | **Narrowly missed** (p95 +14%); cutover anyway, see below |
| Invariant and update-equivalence tests green | KG gate in CI; 240/240 real commit pairs (M7) | ✅ |

## The decision, and the evidence behind it

| System | T2 R@budget | T2 `sym_code` | T2 `sym_tests` | T1 deps / impact R@budget | T3 sufficiency |
|---|---|---|---|---|---|
| S2 (v1, what production served) | .045 | .068 | .034 | .049 / .201 | .145 |
| A_tuned (best non-learned) | .642 | **.673** | .594 | .554 / .886 | .974 |
| E+A (RRF) | .630 | .646 | .591 | **1.000 / .995** | **1.000** |
| F_nocc (M9, as trained) | .686 | .624 | .682 | .772 / .995 | .980 |
| **V2** (F_nocc + callee pin, no overlay) | **.681** | .624 | .674 | .962 / .995 | **1.000** |

**Why cut over despite the latency criterion.**
- §5.7's figures are design targets per stage. The review they serve waits seconds for the LLM, so 193 ms at p95 is not user-visible.
- The overlay rebuild, which would have made it 345 ms, is already removed.
- The remaining cost is the reranker's feature computation: a 5,000-document lexical scoring pass, PPR and a two-hop BFS per review, all in pure Python. That is the first optimisation target (score only pool members; reuse the PPR vector for the BFS).
- Holding the cutover for 23 ms would keep production on a pipeline (v1) that delivers the needed context for one injected bug in seven (T3).

No system wins every column. V2 is chosen because it is the only one that is good on all three kinds of evidence:
- **On real co-changes (T2)** it is +.039 over A_tuned (p .02) and +.051 over E+A.
- **On structural need (T1)** it is close to E+A.
- **On bug-relevant context (T3)** it is at the ceiling.

Its known weakness: **code-only co-changes** (`sym_code`). There it trails A_tuned by .048 (p .07, n.s.); its T2 gain comes from tests. If reviewers turn out to need test context less than T2 assumes, A_tuned would be the better choice on T2. Only the LLM detection run of T3 (paid, not run) can settle what reviewers actually need.

## Not done in M11

- **v1 removal.** By design, v1 code and tables stay for one release as the rollback. Under v2, pushes no longer re-index v1, so after a while on v2 a rollback serves a stale v1 index until the next v1 full index.
- **JS/TS extraction via tree-sitter.** Listed as a follow-on in §9. The v2 extractor is Python-only. **A diff that touches no Python file is served by v1** (`get_context_v2` returns None; tested), so JS/TS reviews do not regress at the cutover. Mixed diffs get v2 context for their Python part only.
- **Alembic migrations.** As in M7.
