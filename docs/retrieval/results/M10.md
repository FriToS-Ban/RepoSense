## What was built

**T3 v1.0: 152 injected bugs in real code.** The cases come from the six T2 repositories at their pins, and each needs context from another file to be caught:

| Mutation | Cases | What the reviewer needs to see |
|---|---|---|
| `arg_swap`: the first two positional arguments of a cross-file call are swapped | 35 | the callee's signature |
| `drop_arg`: a cross-file call loses a required trailing argument | 60 | the callee's signature |
| `add_param`: a function called from other files gets a new required parameter; callers unchanged | 57 | a caller's call site (the call-site window or the full body) |

- **Site selection.** Mutation sites are chosen with the **frozen reference resolver** (`eval/reference`), never with the system under test. A call qualifies only when the reference resolver binds it to exactly one cross-file target. Sampling is seeded by hash per (repo, type), 10 per cell; httpx, starlette and attrs have fewer qualifying `arg_swap` sites.
- **Diff.** The single mutated line in a ±3-line hunk. The base is the pin; HEAD is the mutated file.
- **Two measurements:**
  - **Context sufficiency (free, offline):** is the needed item in the packed context, in a rendering that shows what is needed? Any rendering shows a callee's signature. A caller counts only with its call site or full body.
  - **Review detection (paid):** `run_t3 --llm` sends the production review prompt, parsed from `backend/services/llm.py`, with each system's context to an OpenAI-compatible chat endpoint. A case counts as detected when a comment lands within ±3 lines of the injected line. Every case also has a control (the same line plus a harmless trailing comment) to measure false positives. The run refuses to start without `LLM_BASE_URL`, `LLM_MODEL` and `LLM_API_KEY` in the environment.

## Context sufficiency

| System | All (152) [95% CI] | arg_swap | drop_arg | add_param |
|---|---|---|---|---|
| **S2** (v1 as in production, hot-fixed) | **.145** [.086, .204] | .057 | .067 | .281 |
| A (lexical) | .961 [.928, .987] | 1.00 | .98 | .91 |
| E (graph, 1-hop) | 1.000 | 1.00 | 1.00 | 1.00 |
| E+A | 1.000 | 1.00 | 1.00 | 1.00 |
| E_ppr, E_bfs, PA | 1.000 | 1.00 | 1.00 | 1.00 |
| P (pure PPR) | .967 [.934, .993] | .91 | .97 | 1.00 |

E, E+A and the other graph systems vs A: +.040 (p .032, p_holm .19 over six comparisons).

## Reading

1. **The production gap is large.** v1 puts the needed context in front of the reviewer for one bug in seven. 87.5% of its context is the mutated file itself, which the diff already shows; that is audit finding W2 again. Every v2 system delivers it for 96–100% of cases. Of everything measured so far, this is the strongest argument for the cutover (M11).
2. **For these bug classes, retrieval among v2 systems is not the bottleneck.** The needed symbol's name is on the changed line, so BM25F finds the callee (100% / 98%). A misses 6 of 152 cases: five `add_param` callers and one `drop_arg` callee. All six are candidate-generation failures: the needed symbol is never among A's 40 candidates. A caller is linked to the changed signature only by a call edge, which the graph channel follows directly. Graph systems reach the ceiling. T3 as built cannot separate the v2 systems. A harder T3 would need bugs whose context is *not* named on the changed line: violated docstring preconditions, return-contract misuse, a base method removed under a `super()` call.
3. **The question T3 exists for is still open.** Does the context change what the LLM catches? Sufficiency is necessary for detection, not sufficient, and the T2 results (M4) show that more context items also mean more noise. The detection run is ready. It costs about 152 cases × (systems + 1 control each) chat calls, and it is the paid step the roadmap reserves for the user's approval.
