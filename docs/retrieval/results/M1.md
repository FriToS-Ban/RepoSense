The v2 graph is built, stored and validated, but **not yet used by the review pipeline**. Production still runs the (hot-fixed) v1 retrieval. M2 connects the two.

## What was built

| Module | Role |
|---|---|
| `model.py` | `FileFacts` (per-file, JSON-cacheable), `Symbol` / `Edge` / `Graph`, tiers, flags, `symbol_id = sha1(repo, path, qualname)` |
| `extract_python.py` | Pure per-file extraction (stdlib `ast`), producing: <ul><li>module, class (incl. nested), function and method symbols</li><li>merged `@overload` / property / `TYPE_CHECKING` variants</li><li>imports with their binding scope (incl. function-local)</li><li>every maximal name/attribute chain read, with owner, role and scope</li><li>local and module-level type facts</li></ul> |
| `resolve.py` | Global name resolution: one state machine (module, namespace package, class, instance, symbol, super, external), tiers R1–R5, edges aggregated per `(src, dst, type)` with evidence lines and roles |
| `derive.py` | C3 MRO (DFS fallback), `OVERRIDES` (incl. `implements_abstract`), `TESTS` (direct / via helper / naming convention) |
| `build.py` | `build_graph`, `validate` (invariants 1–4 of design §3.6) |
| `store.py` | Transactional diff-apply into `kg_symbols` / `kg_edges` / `kg_snapshots`; extraction cache `kg_files`; vector outbox `kg_vector_outbox` |
| `snapshot.py` | Immutable CSR view: neighbours by edge type and direction, `innermost(path, line)` |

Tests: 20 in `backend/tests/test_kg.py`, all green, plus the 3 M0 regression tests. They cover:
- every resolution tier
- shadowing by locals and function-local imports
- re-exports, star imports, `src/` layouts and namespace packages
- generic bases
- R5 scoping and the builtin-name exclusion
- MRO including the inconsistent-hierarchy fallback
- OVERRIDES / TESTS
- invariant detection
- store idempotence and **update equivalence** (apply(A) then apply(B) equals a fresh build of B)
- outbox rows on deletions
- rollback on an invariant failure
- snapshot neighbours and line lookup

## Exit criteria

| Criterion (design §9) | Result |
|---|---|
| Invariants green on all corpora | **0 violations** on all 6 T1 corpora and the 97k-LOC merged corpus |
| Per-tier precision measured | Held-out gold sample, 210 edges (table below) |
| R1–R3 precision ≥ .95 on gold | **1.00** for each (40/40; Wilson 95% lower bound .91) |

| R5 | import-scoped fallback for `x.m()` with unknown `x` | 28 / 50 | .56 | [.42, .69] | .558 |
| R5, 1 candidate | | 15 / 18 | .83 | | .800 |
| R5, 2 candidates | | 5 / 15 | .33 | | .353 |
| R5, ≥3 candidates | | 8 / 17 | .47 | | .474 |

**Recall** on 81 exhaustively labelled call sites: in-repo calls **25/26 = .96** (Wilson [.81, .99]). The one miss is `github.Repository.Repository`, whose defining file (220 KB) is excluded by the 100 KB per-file ingestion cap (see Findings). Of 54 calls to builtins, external libraries or dynamic callables, 53 were correctly left unresolved; the one false positive came from R5.

Calibration uses the **Laplace posterior mean** (k+1)/(n+2), not the Wilson lower bound proposed in design §3.4. With 40/40 per tier, the Wilson bound (.91) would rank tiers by *sample size* rather than accuracy, whereas the posterior mean is the calibrated point estimate. The confidence is a ranking feature, so ordering matters more than conservatism.

### How the sample was protected from tuning

1. A **development sample** (210 edges, resolver 1.0) was labelled first and used only to find errors. Result: R1–R4 all correct; R5 15/50 = .30.
2. Fixes from that review, together producing kg-py-1.1:
   - R5 no longer guesses method names that builtin types or loggers carry (`.get`, `.items`, `.append`, `.update`, `.info`, …): the development sample's dict/list-method guesses were 0/24 correct.
   - R4 gained module-level instances (`NotSet = _NotSetType()`) and return-annotation inference (`x = f()` with `def f() -> Cls`, nested to depth 3).
   - `cls.x` no longer produces an edge to the method's own class.
   - Annotation roles propagate into subscripts (`list[Server]`).
   - `if TYPE_CHECKING: def X` + `else: class X` keeps the class.
3. A **fresh, hash-selected sample** (salt `gold-v1`) was then labelled. That is the table above. 25 of its 210 items coincide with development items by chance.
4. After scoring, one **extraction bug** was fixed (kg-py-1.2): generic bases `class Request(HTTPConnection[StateT])` were not resolved. Inheritance edges in starlette went from 22 to 32 and in PyGithub from 196 to 203; starlette overrides went from 37 to 52. This only adds edges through the R1–R3 mechanisms. kg-py-1.2's tier precision was **not** re-measured; recall is unchanged (.96).

v1 for comparison:
- 0% of function nodes had any outgoing edge
- no same-file call edges
- bare-name call edges were 35–45% precise on larger repositories
- indexing the merged corpus took 24.5 s of CPU plus about 26k sequential network calls

A no-op re-index reuses every cached file, re-runs global resolution, and changes **0 rows** on every corpus.

**Agreement with the frozen reference resolver** (a consistency check, not a quality measure): v2 recovers 100% of the reference's pairs on 5 corpora and 99.95% on pydantic. The single difference is a reference error: a function-local `from eval_type_backport import eval_type_backport` shadows a module-level function of the same name, and only v2 handles it.

## Findings

1. **Ingestion drops the most central code.** The 100 KB per-file cap (inherited from v1's crawler) excludes `github/Repository.py` (220 KB) and `github/Organization.py` (116 KB), the core of PyGithub. Large files are disproportionately central. **Action (M7):** lift the cap for source files in the tarball-based acquisition and cap by parse cost instead.
2. **Remaining R5 errors** (22 of 50, held-out), the backlog for the next resolver iteration. Every change must be verified on a fresh gold sample (`gold-v2`).

   | Cause | Count | Remedy |
   |---|---|---|
   | Receiver typed by an external library (requests, httpcore, anyio, jinja2) | 12 | Propagate *external* types from constructors and annotations, and never guess for them |
   | Wrong sibling among the candidates (ParseResult vs URL, GenerateSchema, Response vs Request, ujson vs orjson protocol) | 5 | Property and `cast()` types; rank candidates instead of splitting confidence evenly |
   | Data attribute on a known class called as a function (`self.app(...)`) | 3 | No fallback when the receiver class is known and the attribute is not a method |
   | `Any`-typed receiver | 1 | — |
   | Generic base not resolved | 1 | Fixed in kg-py-1.2 |

3. Static resolution plus light inference resolves 40–41% of all call sites to in-repo code. Most of the rest are builtins or external libraries (spike A). R5 is therefore a small, low-confidence tier by design: 20–91 R5 call edges per corpus under kg-py-1.2.

## Limitations

- Gold labels were produced by the assistant reading source code, not by a human annotator. The labels, items and notes are committed for spot-checking ([gold README](../../../eval/data/kg_gold/README.md)).
- The site-packages corpora contain no tests, so `TESTS` edges are validated only by unit fixtures until T2 (M4).
- The recall sample is small (26 in-repo sites).
- `backend/main.py` will create the new `kg_*` tables on start-up (`create_all`). They stay empty until M2 or M7 call `backend.kg.store.index_files`.
