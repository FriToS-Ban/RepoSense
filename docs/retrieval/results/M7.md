## What was built

**Incremental update (`kg.store.update_files`).** It applies a compare-style change set (`path → new content`, or `None` for a deletion; a rename is both). Only the changed files are re-extracted; all other FileFacts come from the extraction cache (`kg_files`). Resolution then runs globally (ADR-08), the result is validated, and it is diff-applied in one transaction together with the vector-outbox rows and the snapshot flip. A file whose content did not actually change is skipped. If the cache was written by another extractor version, the update refuses and a full index runs.

**A 40× faster diff-apply.** Measuring the update exposed a quadratic cost in M1's `apply_graph`. Every per-edge ORM `UPDATE` made SQLAlchemy evaluate its WHERE clause against every object the session had loaded, about 7k symbols and edges. One click commit (18 files, 434 symbols and 1,683 edges updated because line numbers shift) took **94.7 s, 98% of it in that synchronisation**. The writes are now Core-level executemany statements, followed by `expire_all()` so later ORM reads in the session see fresh rows. The same update takes **2.3 s**. The full index of click went from 1.74 s to 1.49 s.

**Acquisition (`services/kg_indexer.py`).**
- **Full index:** one `GET /repos/{r}/tarball/{sha}` instead of v1's recursive contents crawl, which made one API call per file and directory and capped files at 100 KB. The tarball is read in memory: only regular files, no links, no absolute or `..` paths, `.py` files up to 1 MB, vendored directories skipped. M7 therefore lifts the 100 KB cap, which on T1 dropped `github/Repository.py`.
- **Push:** the compare API between the stored snapshot and the pushed commit lists the changed files. Only those are fetched (raw media type, at the pushed commit) and applied with `update_files`.
- **Fallbacks:**
  - a full index runs when the stored snapshot is not the push's `before` (a missed event or a force-push), or when the compare list is truncated (≥ 300 files);
  - a redelivered event (snapshot already at `after`) is a no-op;
  - only pushes to the default branch count. The graph represents the default branch, and v1 re-indexed on pushes to *any* branch.
- **One writer per repository:** an in-process lock and, on PostgreSQL, a transaction-scoped advisory lock. The snapshot check runs under the lock, so two concurrent pushes cannot both apply a diff to the same base.

**Production wiring behind `RETRIEVAL_ENGINE` (default `v1`, design §8):**
- `rag.get_relevant_context` gains `head_content` and `pr_text`. Under `v2` it calls `context_v2.get_context_v2` and falls back to v1 on any error, so a review never fails because of the new engine.
- `context_v2` keeps an LRU of 4 `RepoRetriever`s keyed by (repo, snapshot commit). It serves System A, the best system measured on T2 so far, and logs a trace summary per review.
- `review.process_pr_review` reads the PR's head SHA and description (`get_pull_request_meta`) and fetches changed files at the head lazily, once per review.
- The push webhook calls the incremental update under `v2`. Enabling a repository runs a full index of the default branch's head under `v2`.

## Update equivalence on real history (exit criterion)

For each T2 repository, the harness indexes the code at the start of a first-parent chain (up to 400 commits before the pin). It then walks the chain and applies every commit as an incremental update, until 40 steps that change at least one code file have been checked. Steps that change no code file are skipped and not counted.

| Repo | Pairs checked | Commits walked | Files changed (total) | Median symbols touched | Median update (s) | **Equivalent** |
|---|---|---|---|---|---|---|
| httpx | 40 | 109 | 150 | 25.5 | 0.49 | **40/40** |
| starlette | 40 | 61 | 100 | 10.5 | 0.62 | **40/40** |
| flask | 40 | 82 | 100 | 26 | 0.33 | **40/40** |
| click | 40 | 54 | 90 | 25 | 0.48 | **40/40** |
| requests | 40 | 87 | 60 | 6.5 | 0.24 | **40/40** |
| attrs | 40 | 120 | 108 | 55.5 | 0.43 | **40/40** |
| **Total** | **240** | 513 | 608 | | | **240/240, 0 problems** |

"Median update" is the whole `update_files` call: extraction of the changed files, global resolution, diff and SQLite writes. The in-memory graph build alone takes 0.06–0.16 s on these repositories. "Symbols touched" counts inserted, updated and deleted symbols. Most updates are line-number shifts below an edit, because spans and evidence lines are stored.

Each step is checked field by field. **Symbols:** every column. **Edges:** confidence to 1e-6, tier, role, weight, evidence lines, roles. **Integrity:** no orphaned edges; extraction cache equal to the file set; no invariant violations; the outbox rows of the step are exactly the deleted symbols (`delete`) and the new or content-changed ones (`upsert`).

## Tests

- `backend/tests/test_kg.py`: an incremental update equals a fresh build (modify, delete, add, ignore non-Python); outbox rows; a no-op update writes nothing.
- `backend/tests/test_kg_indexer.py` (6 tests, fake GitHub client):
  - tarball safety: links, `..` paths, size cap, vendored directories, CRLF
  - full index, then incremental updates (no tarball downloaded, only the changed files fetched)
  - a rename; a redelivered push
  - snapshot mismatch and truncated compare fall back to a full index
  - default-branch push filter
  - the `rag` facade serving v2 context when enabled

48 backend tests pass.

## Not done, and why

- **Alembic migrations** (design §7). The kg_* tables are created by `Base.metadata.create_all` like every other table in the app today. Replacing the startup `ALTER TABLE` SQL is production hygiene, not something retrieval quality or evaluability depends on (design §10, "scope creep"). It is left for the cutover (M11).
- **A persisted trace table.** Traces are logged as summaries, not stored. Replaying production traces offline (design §5.6) needs PR diffs that this repository should not store without a retention decision.
- **Vector outbox consumer.** Rows are written, but there is no dense channel to consume them (M8).
